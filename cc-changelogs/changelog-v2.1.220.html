Clearer beta-header retry log message #

New

When Claude Code sends a beta API header and the server rejects it with HTTP 400, it retries without that header and logs a debug message. The wording of that message was tightened for clarity.

Before: "beta rejected (HTTP 400) and the bare retry succeeded — dropping the beta for the rest of the session" After: "beta rejected (HTTP 400) and the retry without it succeeded — dropping the beta for the rest of the session"

This only appears in debug output and has no effect on behaviour.

Evidence

Auto-mode classifier API header [In Development] #

Dev
What

A new API beta header auto-mode-classifier-2026-07-16 is now conditionally sent with requests. This header likely enables a server-side routing or response-mode classification feature.

Status

Feature-flagged — only sent for first-party Anthropic users who pass two additional internal checks (HP() and Yd()). Not active for standard users.

Details
  • ROd(e) is called exclusively inside the two-stage auto-mode classifier pipeline, once for Stage 1 ("xml_s1" — a fast yes/no call capped at 256 output tokens) and once for Stage 2 ("xml_s2" — a deeper analysis call capped at 8192 output tokens). Regular chat, agent, and tool-use API calls never receive this header via this path.
  • Three conditions must all be true for the header to be appended: (1) the provider type of the classifier's model (resolved via ny(o)) must be exactly "firstParty"; (2) HP() must return true — the session auth type is firstParty, anthropicAws, anthropicGoogleCloud, or foundry, AND CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS is not set, AND the session is not in HIPAA mode; (3) Yd() must return true — either the internal env var _CLAUDE_CODE_ASSUME_FIRST_PARTY_BASE_URL is set, or ANTHROPIC_BASE_URL is unset or resolves to exactly api.anthropic.com.
  • When all conditions pass, ROd returns [Sji]. This single-element array is spread into extraBetas on the classifier request, causing the anthropic-beta: auto-mode-classifier-2026-07-16 header to be included alongside any other beta headers for that call.
  • Users on third-party providers (bedrock, vertex, foundry, mantle), on a custom ANTHROPIC_BASE_URL, in HIPAA mode, or with CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS set will never have this header sent, even when the auto-mode classifier is active.
  • The header value follows the same dated-slug convention used by other active beta headers in the registry (e.g. mcp-servers-2025-12-04, per-turn-control-2026-07-01).
Evidence

new header constant Sji = WA("auto_mode_classifier", "auto-mode-classifier-2026-07-16") added to the request-header registry (search for "auto-mode-classifier-2026-07-16"); ROd (line 515658) passes the header as extraBetas in the Stage-1 (xml_s1) and Stage-2 (xml_s2) classifier API calls at lines 515302 and 515419 respectively

Claude Opus 5 model constant [In Development] #

Dev
What

A new model identifier claude-opus-5 has been registered internally, along with gating logic that deliberately excludes it from normal model resolution and fallback paths.

Status

Stubbed — the constant exists and detection functions are wired up, but the model is explicitly filtered out of all fallback resolution so users cannot reach it through any current code path.

Details
  • claude-opus-5 is fully registered in the model registry — not a bare stub. The entry includes: family: "opus", display_name: "Opus 5", knowledge_cutoff: "May 2026", a 1 million-token native context window (native_1m: true, no beta suffix required), max_output_tokens: { default: 64000, upper: 128000 }, pricing: "tier_5_25", advisor_rank: 4, and the capability set [effort, max_effort, xhigh_effort, adaptive_thinking, mid_conv_system, context_management, fast_mode, lean_prompt].
  • Provider IDs are populated for every platform: first_party: "claude-opus-5", bedrock: "us.anthropic.claude-opus-5", vertex: "claude-opus-5", foundry: "claude-opus-5", anthropic_aws: "claude-opus-5", anthropic_google_cloud: "claude-opus-5", mantle: "anthropic.claude-opus-5", gateway: "claude-opus-5". Both bedrock and vertex have eager_input_streaming: true. The model declares fallback_3p: "claude-opus-4-8" for third-party fallback chains.
  • The model is the default resolution target for the opus alias on first_party, bedrock, vertex, mantle, and anthropic_aws providers, and is recorded as latest_per_family.opus. It also receives the internal short-name mapping "claude-opus-5" → "opus5" used in telemetry and the model-options UI.
  • Xkt() — exported as isEntitlementOverlayUnavailable — returns true when the client is in an entitlement-blind state: Hn() === "firstParty" (provider is first-party), zA() is true (an OAuth accessToken is present, i.e. the user is logged in via claude.ai), !bH() is true (user is NOT in a scope that includes the restricted-access flag q0e), eZ() === null (no API key is configured), and ZJt().length === 0 (the server-side model access cache is empty — entitlements have not yet been fetched).
  • During this entitlement-blind state, u2c(e) (Xkt() && Ooe(e) === rdg) is true for any request targeting claude-opus-5. d2c(e) then silently redirects the model to c2c = "claude-opus-4-8", and the fallback-walk function f2c() skips any candidate where u2c(n) is true. Once the entitlement cache populates (ZJt().length > 0), Xkt() returns false and all redirect/skip logic is bypassed, making the model accessible normally.
  • The Xkt() state is recorded in telemetry as entitlement_blind: true on both tengu_rotunda_pennant_applied (server-fallback) and tengu_refusal_fallback_route_declined events, allowing Anthropic to correlate model-switching behaviour with the entitlement-loading phase.
  • XMu = "claude-opus-4-8" is a separate constant defined in the auto-compact section (line 275969). It is used only by Bds(e), a function that looks up a compact-token threshold for that specific model; it is not related to the c2c = "claude-opus-4-8" constant used in the entitlement redirect path.
